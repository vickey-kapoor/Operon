## 1. Summary

Operon's current architecture (v1) pairs strong reliability primitives — vision-first perception, verify-after-every-action, a recovery ladder, deterministic-rules-before-LLM, and total run observability — with a **monolithic, synchronous control loop**: one LLM call per step decides *what to do* and *where to click*, one action at a time, with forward-only recovery and no learning between runs.

This RFC proposes **v2**: keep every reliability primitive, but restructure the control flow around three ideas the market's SOTA systems and benchmarks point to as the real levers:

1. **Planner / Grounded-Actor split** (slow System-2 planning + fast System-1 grounded action).
2. **Verification-driven search** that closes the `pass@1 → pass@k` gap (Best-of-N + rollback), reusing Operon's existing verifier.
3. **A data flywheel** over the artifact store we already produce (reflect → skills + fine-tuning data).

Plus a first-class **trust gate**, an **async engine**, and **swappable grounding** as a first-class model.

## 2. Motivation

**Evidence (see [`../PRD.md`](../PRD.md) §15 for sources):**
- **`pass@k` ≫ `pass@1`** across every benchmark (e.g. Surfer 2 OSWorld 60.1% → 77.0% pass@1→pass@10; Agent-S3 66% → 72.6% with Best-of-N). The biggest reliability lever available is *productizing test-time search* — and Operon already has a strong deterministic verifier to drive it.
- **GUI grounding is the #1 documented failure mode** (OSWorld). Relying on a CUA model's raw coordinates leaves accuracy on the table; SOTA systems use *dedicated grounding* (UI-TARS, Agent-S "mixture-of-grounding").
- **Hierarchical / proactive planning** (replan after each subgoal, not only on error) is Agent-S3's headline gain.
- **Data flywheels** (UI-TARS) compound: harvest traces → filter → retrain. Operon persists everything already — a rare, ideal substrate that closed CUAs don't expose.
- **Prompt injection is OWASP LLM01 (#1 LLM risk)** and the "assumes outcomes without checking" failure validates verify-every-action. Trust must be architectural.

**The ceiling is the control flow, not the primitives.** v2 is a re-architecture of *how steps are produced and selected*, not a rewrite of what works.

## 3. Goals / Non-goals

**Goals**
- Materially raise single-attempt task success on a curated internal suite (browser + desktop).
- Cut grounding errors via a swappable, independently-measurable grounding layer.
- Make reliability *tunable* (search depth) and *learnable* (flywheel).
- Make safety/trust a mandatory, audited path — not a hook.

**Non-goals**
- Not a clean-sheet rewrite. v1's primitives are preserved (see §5).
- Not training a frontier model. Operon's value is the harness; it consumes the best models.
- Not abandoning vision-first (see Move 7 — explicitly recommended *against*).

## 4. Proposal — the 7 moves

Each move: **Problem → Proposal → Alternatives considered → Risks.**

### Move 1 — Planner (System-2) / Grounded Actor (System-1) split
- **Problem.** One model call per step conflates goal decomposition with pixel grounding; no proactive replanning.
- **Proposal.** A **Planner** decomposes the goal into a subgoal queue and *replans after each completed subgoal* (proactive, not error-only). A fast **Actor** turns `subgoal + screenshot → one action`. Different model/cost tiers per role.
- **Alternatives.** (a) Keep monolithic loop — simplest, but caps planning quality. (b) Full multi-agent "swarm" (Skyvern-style) — more flexible, much harder to make deterministic/observable. Chosen: a 2-tier split as the minimal structure that buys proactive planning without losing determinism.
- **Risks.** Planner/Actor handoff adds latency and a new failure surface; mitigate by allowing the Actor to short-circuit trivial subgoals and caching plans.

### Move 2 — Grounding as a first-class, swappable model (Mixture-of-Grounding)
- **Problem.** Reliance on the CUA model's raw coordinates; grounding is the #1 failure and is not independently measurable.
- **Proposal.** A `Grounder` interface: `(intent, screenshot) → coordinate(s) + confidence`. Pluggable backends — the CUA's own coords, a UI-TARS-style grounding model, or OmniParser-style set-of-marks — selectable per surface. Measured in isolation against a grounding benchmark (ScreenSpot-class).
- **Alternatives.** (a) Trust CUA coords only — zero new infra, but no ceiling lift. (b) Always set-of-marks — strong but adds a parsing pass and latency everywhere. Chosen: an interface so we can A/B grounders per surface with data.
- **Risks.** A second model per step = cost/latency; mitigate by only invoking the heavy grounder on low-confidence or high-risk actions.

### Move 3 — Verification-driven search (close `pass@1 → pass@k`)
- **Problem.** One action per step, verified, recovered linearly. The benchmark gap says multiple candidates + selection wins big.
- **Proposal.** At hard/uncertain steps: Actor proposes **N candidate actions**; the existing deterministic **Verifier + a learned critic** score them; execute the best; **checkpoint state to enable rollback/branching** rather than forward-only recovery. Search depth is a tunable reliability/cost knob.
- **Alternatives.** (a) Keep linear recovery — cheapest, leaves the largest known win unclaimed. (b) Full tree search/MCTS — maximal, but state checkpoint/restore on live UIs is expensive and sometimes impossible. Chosen: shallow Best-of-N with opportunistic rollback — most of the gain, bounded cost.
- **Risks.** State checkpoint/rollback is hard on non-transactional UIs (side effects already happened). Mitigate: gate branching to *read-mostly* / reversible steps; never speculate through the trust gate's high-risk actions. **This is the recommended first experiment — see §7.**

### Move 4 — Data flywheel over the artifact store
- **Problem.** We persist everything but learn nothing between runs; the absent `PostRunReflector` is a real gap.
- **Proposal.** Add a `PostRunReflector` that harvests traces → reflective filtering (keep successes + instructive failures) → distills into (a) reusable **skills/macros** (parametrized action sequences for recurring workflows) and (b) **fine-tuning datasets** for the grounder/critic.
- **Alternatives.** (a) Manual skill authoring — predictable, doesn't scale. (b) Pure RL from traces — powerful, heavy, slow to stand up. Chosen: reflection→skills first (cheap, immediate), fine-tuning data as a parallel output.
- **Risks.** Bad traces poison skills; mitigate with verifier-gated acceptance and human review of promoted skills.

### Move 5 — Trust gate as an architectural layer
- **Problem.** Safety today is HITL + deterministic guards — good, but not a mandatory chokepoint; prompt injection is the #1 risk.
- **Proposal.** A **Trust Gate** every action passes between Actor/search and Executor: untrusted-content isolation (treat all on-screen text as hostile), an injection classifier on perception, user-authored **allow/deny policies**, **high-risk-action confirmation gating**, and sandbox/VM execution guidance. Delivers PRD v0.2 items FR-12 / FR-16 as core.
- **Alternatives.** Keep guards scattered in policy — lower effort, weaker guarantee/auditability. Chosen: a single audited chokepoint.
- **Risks.** Over-gating harms autonomy; make policies configurable with safe defaults and clear audit logs.

### Move 6 — Async, event-driven engine
- **Problem.** Synchronous per-step loop; one run per executor; blocking verification — and it *can't* express Move 3's branching.
- **Proposal.** An async engine with streaming perception, non-blocking verification, and an event bus feeding the flywheel. Enables parallel/speculative exploration (cf. Project Mariner's 10 parallel tasks).
- **Alternatives.** Thread-per-run on the sync loop — incremental, but doesn't unlock branching/streaming cleanly. Chosen: async core as the substrate for Moves 3 & 4.
- **Risks.** Concurrency bugs; mitigate with strict per-run state ownership and the existing per-run artifact isolation.

### Move 7 — [Recommended AGAINST] Hybrid DOM/accessibility grounding-assist
- **Problem.** Pure vision sometimes grounds worse than a stable handle would.
- **Proposal (declined).** Allow a DOM/accessibility signal *only* as grounding/verification assist where cheaply available.
- **Recommendation.** **Do not adopt now.** It cuts against Operon's "zero-abstraction, no-DOM" brand and reintroduces the selector-fragility we differentiate against. Revisit only if Move 2's data shows vision grounding is the binding constraint on a surface we must win. Documented so the decision is explicit, not accidental.

## 5. What v2 keeps from v1 (unchanged)

Vision-first perception · the `Environment` executor abstraction · verify-after-every-action · the recovery primitives (now feeding search) · full per-run artifact observability · deterministic-rules-before-LLM · model-agnosticism · the Tauri shell · the FastAPI surface.

## 6. Migration plan (incremental — no big-bang)

A clean-sheet rewrite would forfeit the reliability edge. Sequenced by ROI / blast-radius:

1. **Grounding layer (Move 2)** behind the current interface — swappable, measurable alone.
2. **Best-of-N at hard steps (Move 3)** reusing today's verifier — biggest reliability ROI, smallest blast radius. *(First experiment, §7.)*
3. **Planner/Actor split (Move 1)** — restructure the loop once grounding + search are stable.
4. **Trust gate (Move 5)** — also ships PRD v0.2.
5. **Flywheel + reflector (Move 4)**, then **async engine (Move 6)** underneath.

Each lands behind a flag with before/after metrics on the curated suite; no step regresses `pass@1` or the zero-unverified-success invariant.

## 7. First experiment — Best-of-N at hard steps (Move 3)

- **Hypothesis.** Proposing N=3 candidate actions at low-confidence steps and selecting via the existing verifier + a lightweight critic raises single-attempt task success on the curated suite by a meaningful margin, at bounded extra token cost.
- **Design sketch.** Trigger only when policy confidence < threshold (reuse the existing confidence signal). Actor samples N candidates; score each (verifier heuristics + critic); execute the top; if it fails verification and the step is reversible, roll back and try the next. No branching through high-risk/irreversible actions.
- **Success metric.** ≥ X-point lift in suite `pass@1` with ≤ Y% median token-cost increase and **zero** new unverified-success incidents. (X/Y set when the suite baseline is measured.)
- **Kill criteria.** No measurable lift, or rollback proves unsafe on live UIs (irreversible side effects), or latency/cost exceeds budget.
- **Why first.** Reuses existing verifier; flag-gated; isolated from the core loop; directly tests the RFC's biggest claim with real numbers.

## 8. Open questions / decisions needed

1. **Grounding backend** for the Move 2 spike: CUA-coords baseline vs. an open grounding model vs. set-of-marks?
2. **Rollback scope** in Move 3: which action classes are "reversible enough" to branch through?
3. **Critic**: heuristic-only first, or a small learned critic from day one?
4. **Flywheel governance**: auto-promote skills behind the verifier, or require human review?
5. **Async migration**: rewrite the loop, or strangler-pattern alongside the sync loop?
